# Blaster administration guide

[Project overview](../README.md) · [Architecture](architecture.md) · [Security review](security-review.md)

This guide operates the consolidated repository. It does not administer either original deployment. Run commands from this repository's root and review `.env` before starting services.

## 1. Prepare the environment

Install Docker Compose and Python 3.12+. Backend services must already provide RAG on host port 15002, inference on 18030, and the agent API on 18040. Adapt the public route manifest for your own services.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

Set `BLASTER_TLS_DIR` to an existing directory outside the repository containing the operator's `tls.crt` and `tls.key`. No TLS material is supplied or generated by this project. Use a certificate trusted by your client and a protected private key. Do not copy deployment certificates, subjects, serials, fingerprints, or signing material into Git, documentation, screenshots, or Vault examples.

The safe local bind is `127.0.0.1:8443`. For a LAN deployment, choose your own assigned address. Documentation uses only the fictional host `192.168.15.10` and gateway `192.168.15.1`; Compose does not assign either address.

## 2. Prepare consumer credentials outside Git

Create a private operator directory and two generated API-key files:

```bash
install -d -m 700 "$HOME/.config/blaster"
.venv/bin/python tools/create_key.py "$HOME/.config/blaster/demo-user.key"
.venv/bin/python tools/create_key.py "$HOME/.config/blaster/agent-service.key"
```

The generator refuses existing files and paths inside this repository. It never prints the key value.

For an initial local review without Vault, assemble the external private mapping:

```bash
umask 077
python3 - <<'PY'
import json
from pathlib import Path
private = Path.home() / '.config/blaster'
values = {name: (private / (name + '.key')).read_text().strip()
          for name in ['demo-user', 'agent-service']}
(private / 'consumers.json').write_text(json.dumps(values))
PY
.venv/bin/python tools/render_config.py --secrets-file "$HOME/.config/blaster/consumers.json"
```

Never paste the mapping or its values into tickets, terminal recordings, or commits. The public placeholder `XXXXXX` is deliberately rejected as an operational credential.

## 3. Validate and start the gateway

```bash
docker compose config --quiet
docker compose up -d edge apisix
docker compose ps
docker compose logs --tail=100 edge apisix
```

The renderer creates the runtime directory before Compose starts. Run it as a non-root operator with a non-root primary group. The startup wrapper prepares writable APISIX state and drops privileges to that directory owner before serving requests. Missing TLS files, missing runtime output, or invalid keys should stop startup/preparation; no working sample key is shipped.

Check syntax and local edge liveness, using your real trusted CA bundle:

```bash
docker compose exec edge nginx -t
curl --fail --silent --show-error --cacert /secure/path/ca-bundle.pem \
  https://192.168.15.10:8443/healthz
```

For actual local loopback testing, use a hostname/IP covered by your own certificate. The fake address is not a connection to a bundled demo server.

## 4. Verify authentication and service scope

Use a private header file, outside the repository, so a real credential need not appear in command history or process arguments. It contains one `apikey: ...` line and must have mode `600`.

```bash
curl --cacert /secure/path/ca-bundle.pem --silent --show-error \
  -o /dev/null -w '%{http_code}\n' \
  https://192.168.15.10:8443/api/inference/v1/models
# Expected: 401, with no API key.

curl --cacert /secure/path/ca-bundle.pem --silent --show-error \
  -H @/secure/path/demo-user.headers \
  -o /dev/null -w '%{http_code}\n' \
  https://192.168.15.10:8443/api/agent/health
# Expected: 403, because demo-user is outside the agent allowlist.
```

Verify successful inference with the demo-user credential, successful agent health with agent-service, invalid-key rejection, and the same protections on legacy aliases. A backend `502` is not a successful integration check even if authentication passed.

## 5. Vault administration

The optional profile provides a local, single-host administration service, not a production Vault cluster:

```bash
docker compose --profile administration up -d vault
export VAULT_ADDR=http://127.0.0.1:18200
vault status
```

Install the Vault CLI separately. Initialize a new server only once, through an approved operator procedure. Keep initialization output and unseal/recovery material in your organization's approved external custody; none belongs in this repository. Unseal interactively when required:

```bash
vault operator unseal
vault login -method=token
```

Use the privileged operator session only for provisioning and maintenance. For a fresh Vault instance, enable the KV v2 mount, store the two private key files, and install the reader policy:

```bash
vault secrets enable -path=apisix kv-v2
vault kv put apisix/consumers/demo-user key=@"$HOME/.config/blaster/demo-user.key"
vault kv put apisix/consumers/agent-service key=@"$HOME/.config/blaster/agent-service.key"
vault policy write blaster-reader vault/reader-policy.hcl
umask 077
vault token create -policy=blaster-reader -no-default-policy -ttl=24h -field=token \
  > "$HOME/.config/blaster/vault-reader.token"
```

The `kv put` commands print secret metadata, not the key value; avoid copying deployment metadata into the public repository. Use an appropriate renewable authentication method for long-lived operation; the example token expires and must not be treated as permanent.

Render through the scoped reader:

```bash
.venv/bin/python tools/render_config.py \
  --vault-token-file "$HOME/.config/blaster/vault-reader.token" \
  --vault-address http://127.0.0.1:18200
```

The renderer checks token policies and refuses `root`. It permits HTTP only for loopback; remote Vault endpoints must use HTTPS with normal CA verification. The local Vault config contains no certificate files, encoded certificate material, fingerprints, subjects, serial numbers, or actual token values.

APISIX uses the last successful runtime file when Vault is sealed. That supports continued serving, but Vault deletion or sealing **does not revoke an already-rendered consumer key**. Revocation requires a successful render and live verification.

## 6. Add a consumer

1. Choose a nonsecret consumer name and generate its private key using `tools/create_key.py`.
2. Store it under `apisix/consumers/NAME` in Vault, or add it to the external private JSON mapping.
3. Add the name to `consumers` and the intended service allowlists in `config/routes.yml`.
4. Run the renderer. It requires an exact credential/consumer match and explicit valid service allowlists.
5. Verify permitted requests, forbidden service access, and missing/invalid credentials.

The manifest is the reviewable source of truth for names, routes, and permissions. Keys remain external.

## 7. Rotate or revoke a key

For rotation, generate a new private file, update the external secret store, render successfully, and verify both that the new credential works and the previous credential fails. Do not print either value in an operations report.

For revocation, remove the consumer from the manifest and all allowlists, update the external JSON mapping if used, then render and verify rejection of the old key. Remove the Vault entry after the successful gateway update. Deleting a Vault entry first can make rendering fail while the previous runtime file continues accepting the old key.

APISIX reload behavior and existing long-lived requests affect the revocation window. Confirm the applied state; do not equate a changed source file with completed revocation.

## 8. Add or change a service

Edit `services` and `routes` in [config/routes.yml](../config/routes.yml). Define an explicit backend port and consumer allowlist, then add exact or prefix rewrites. This single-host profile deliberately accepts only `host.docker.internal:PORT` backends; extending to remote services requires a reviewed TLS/authentication design.

Run checks and render before testing the new route:

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python tools/check_docs.py
.venv/bin/python tools/security_scan.py
```

The agent API and Langfuse integration described in the source are external services. Do not add an unauthenticated GUI catch-all or restore a direct legacy backend location to work around a routing problem.

## 9. Reload, rollback, and recover

Validate NGINX before reloading it:

```bash
docker compose exec edge nginx -t
docker compose exec edge nginx -s reload
```

APISIX observes the standalone runtime file. Check its applied behavior after rendering; if a selected image does not reload as expected, use a controlled APISIX restart and recheck authentication.

For a policy rollback, restore a reviewed manifest from a known Git version and render with the **current** authorized credential set. Do not restore a sensitive runtime backup blindly: it can reactivate revoked keys. Runtime backups, if required, must stay encrypted and outside this repository.

After a Vault restart, perform manual unseal according to custody policy, obtain a valid reader credential, render, and verify. No automatic unseal helper or initialization-key lookup is included.

## 10. Health, logs, and shutdown

```bash
docker compose ps -a
docker compose logs --tail=200 edge
docker compose exec apisix tail -n 100 /usr/local/apisix/logs/error.log
docker compose --profile administration logs --tail=100 vault
docker compose down
```

Do not run `down -v` unless you intend to delete the Vault data volume. The normal shutdown retains it.

| Symptom | Check |
| --- | --- |
| `401` | Missing, invalid, or no-longer-active consumer credential |
| `403` | Authenticated consumer outside the service allowlist |
| `404` | No route, wrong prefix, or intentionally unpublished UI |
| `502` | Backend availability, port, host-gateway mapping, and timeout |
| Failed render | Credential file permissions/location, exact consumer set, Vault seal/token state |
| Old key still works | Was rendering successful, did APISIX apply it, and is the request using a bypass port? |
| TLS validation fails | Correct CA, certificate name, and external mount; keep verification enabled |

Before each release, review the [security report](security-review.md), [validation record](validation.md), branches/tags, and `git remote -v`. Publishing source does not deploy the gateway; runtime secrets and deployment identity must remain private.
